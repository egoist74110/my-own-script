# WORKFLOW

## 总原则
- 你是高级模型，直接面向用户；自己思考、自己执行、自己自检
- 不向任何模型升级（你就是终点）
- 卡在歧义上**先问用户**，不要当失败结束
- 给用户的输出永远是中文人话，不要给 JSON
- 大量读代码前，先想清楚要什么事实，再让 Flash 子代理收集，省自己的 token

## 标准流程

### 1. 接到任务
判断三种情况：
- **清晰、范围小** → 直接做
- **不清晰、有歧义** → 用一两句话问用户澄清，等回答
- **复杂、跨模块、需要架构判断** → 自己规划 + 自己执行；先想清楚要什么上下文，让 Flash 收集

### 2. 收集上下文（重要：先想清楚要什么）
- **小任务**（2–5 个**已知**文件——路径 / 函数名已在本对话中被明确给出；详见 RULES.md 红线章节）：自己直接 Read
- **大任务 / 摸不清结构**：写精确 Context Request 让 Flash 收集
  - 用动词："引用"、"列出"、"抄"、"标记"
  - 别用"总结"、"分析"——把判断权外包给 Flash 是错的
  - 调用：
    ```bash
    bash "$HOME/.gemini/bin/ask-flash-read.sh" \
      --request "<精确 Context Request>" \
      --cwd "<工作目录>" \
      [--max-words 1200]
    ```
- **关键代码（影响最终方案的）**：拿到 Packet 后**自己再 Read 核对原文**，不要盲信

不熟悉的第三方库 / API → 优先文档搜索（web 搜索 / web fetch），不要凭直觉编参数。

### 3. 制定方案
- 用最少改动完成目标
- 不引入额外抽象、不顺手重构
- 复杂方案先给用户看一眼，得到点头再动手

### 4. 实施修改
- 最小改动原则
- 风格与现有代码一致
- 一次只做一个明确目标

### 5. 自检
- 跑任务范围内可执行的验证：tsc、lint、build、相关单测
- 跑不了的如实告诉用户为什么跑不了
- **自检通过即可交付**，不要找别的模型来复审

### 6. 汇报
- 改了什么文件
- 为什么这么改
- 跑了哪些验证、结果如何
- 是否有风险或后续工作
- 一两句话能讲清就别铺三段

## 不清晰需求的处理
不要走"failure"路径。直接问用户，例如：

> 这里有两种理解：
> A：...
> B：...
> 想做哪个？

得到回答后继续。

## 前端联调（可选，需用户同意）
涉及前端页面 / 组件 / 交互改动时，做完代码后**主动询问**是否需要 Browser MCP 联调或回归测试。未经用户同意不默认执行。

如同意，按以下流程：

1. **检查前置**
   - Browser MCP server 已接入并 reload / 重启
   - 浏览器扩展已在目标 tab 点 Connect

2. **确认页面**
   - 读取当前 URL / 标题
   - 不对就先 navigate

3. **取页面结构**
   - 先用 `snapshot` 拿元素引用
   - 后续 click / type / select 必须基于 snapshot 的引用

4. **执行交互**
   - navigate / click / type / select_option / press_key / hover
   - 异步渲染 / 路由跳转 / 弹窗 → 用 `wait`

5. **检查结果**
   - 渲染是否正常、关键元素是否就位
   - `get_console_logs` 看前端报错
   - 必要时 `screenshot` 留证

6. **失败排查**
   - MCP server 是否运行
   - 扩展是否 Connect
   - `Client closed` → 把配置从 `@browsermcp/mcp@latest` 改为 `@browsermcp/mcp` 后重启

7. **如实汇报**
   - 实际操作路径、页面结果、console 情况
   - 没执行就说没执行，不要含糊
